Migration

The markup half is a command

The codemod's mapping table is not a transcription of the guide — it is the table the visual gate runs against all 292 screenshots. Every entry has been checked by rendering a real page with it and finding that nothing moved.

It is dry by default, idempotent, and refuses to touch a class list it cannot read statically — clsx(...), :class, class:name are reported with a line number, never rewritten.

How it was built

Seven stages, each gated by the one before

The order is the point: nothing was rewritten until there was a way to prove the rewrite had not changed anything.

00 Baselines

292 screenshots of the original, three viewports, approved before a line changed.

01 Tokens

201 DTCG tokens. Ten skins became token overlays instead of ten stylesheets.

02 Stylesheet

Logical properties, container queries, zero !important. Cascade layers were measured and rejected — they lost 58 declarations to a Bootstrap page.

03 Headless core

A pure state machine and one DOM binder. Every listener on an AbortController, proven with heap snapshots.

04 Adapters

Five bindings, none over 2.1 kB, none containing navigation logic.

05 Presets

56 catalogue variants collapsed to 28 presets of 179 B. One render plan; 392 comparisons prove all five adapters emit identical DOM.

06 Scroll-spy & theming

Ninety lines of easing replaced by two CSS properties, and the browser's own focus and history handling.

Getting started

Install

Three packages for a styled navbar: the tokens, the stylesheet, and whichever adapter matches your framework. @navx/presets is optional — skip it and write your own markup against the same classes.

bash
npm install @navx/tokens @navx/styles @navx/presets @navx/react
#                                                       @navx/vue
#                                                       @navx/svelte
#                                                       @navx/angular
#                                                       @navx/element   ← no framework

Import the CSS once, anywhere in your app — the two files below are the only stylesheets NAVX ships, and neither contains a single !important.

ts
import '@navx/tokens/tokens.css';
import '@navx/styles/navx.css';

// Optional: a skin, and a dark theme.
import '@navx/tokens/skins/dark.css';

Your first navbar

A preset is data — a plain object describing the chrome. Content is a second plain object with your links in it. The adapter renders them. There is no markup for you to write and none for you to keep in sync when the library changes.

Bring your own content

The demo content above comes from @navx/presets/demo/* and exists so these examples render. Yours is the same shape and nothing more: menus, items, and optional children.

ts
import type { NavxContent } from '@navx/presets';

export const content: NavxContent = {
  logo: { src: '/logo.svg', alt: 'Acme', href: '/' },
  menus: [
    {
      items: [
        { label: 'Home', href: '/', current: true },
        { label: 'Products', href: '/products', children: [
          { label: 'Overview', href: '/products' },
          { label: 'Pricing',  href: '/pricing'  },
        ]},
        { label: 'Contact', href: '/contact' },
      ],
    },
  ],
};

Or skip presets entirely

Presets are a convenience, not a requirement. Write the markup yourself and hand it to attach() — the core has no idea whether a preset produced the DOM it is driving.

ts
import { attach, createNav } from '@navx/core';

const root = document.querySelector('.navx');
const detach = attach(root, createNav(), { trigger: 'click' });

// Later — one abort(), every listener, observer and timer gone.
detach();

Submenus, and why there is only one preset here

All three below are justifiedLogoSocialDualSpaced. Identical chrome, identical machinery — what differs is the content you hand it. That is the collapse that turned 56 legacy variants into 28 presets, and it is the reason a dropdown and a megamenu are not two features to learn.

Click a link with a chevron. Every level is a real disclosure button following the APG Disclosure Navigation pattern — not role="menubar", which promises arrow-key semantics a website navigation does not have.

Scroll-spy

Marks the link whose section you are reading. The legacy implementation cached offsetTop and re-measured on resize, which quietly went wrong whenever anything above a section changed height. Smooth scrolling is scroll-behavior and scroll-margin-block-start — native CSS, replacing about ninety lines of requestAnimationFrame easing, and suppressed automatically under prefers-reduced-motion.

Options

attach(root, machine, options)

Binds a machine to real DOM and returns a detach. Every listener, observer and timer is registered against one AbortController, so detach() is a single abort() — there is no list of teardowns to keep in sync with a list of setups.

OptionTypeDefaultWhat it does
trigger'click' | 'hover''click'How a submenu opens in bar mode. Panel mode is always click.
hoverCloseDelaynumber150Grace period before a hovered-away menu closes, in ms.
dismissOnOutsidebooleantrueClose everything when a pointer goes down, or focus lands, outside the nav.
modalbooleanfalseTrap focus in the open drawer, inert the rest of the page, lock body scroll.
labelDisclosure(linkText: string) => string—Accessible name for a submenu button. Defaults are English — pass your own rather than shipping an English word inside an Arabic navbar.
labelTogglerstring'Menu'Accessible name for the panel toggler.
labelClosestring'Close'Accessible name for the panel close button.

spy(root, machine, options)

A separate subpath, @navx/core/scrollspy, so a nav that does not need it does not pay for it. It observes and writes SPY_SET to the machine; it never touches the DOM itself, which keeps the single-DOM-writer rule intact.

OptionTypeDefaultWhat it does
offsetnumber0Pixels of room above a section — usually your sticky header’s height. Sets scroll-margin-block-start and positions the activation probe.
smoothbooleantrueSet scroll-behavior: smooth on the scrolling element. The browser suppresses it under prefers-reduced-motion.
scrollerHTMLElementdocumentElementOverride when your page scrolls inside a container.

plan(preset, content, options)

The pure function every adapter goes through. Preset and content in, a node tree out — no DOM, no framework, no side effects. All five adapters walk the same tree with toTree(), which is why they can be proven to render byte-identical markup.

labelTogglerstring'Menu'Passed through to the rendered toggler.

Tokens & customization

Three tiers, and only one of them is yours

231 custom properties in three layers. Primitives are raw values and are not public API — they exist so the layer above has something to point at. Semantic tokens name a role rather than a colour. Component tokens are what a navbar actually reads.

Override at the semantic tier and every component that uses that role follows. Override at the component tier to change one thing without disturbing the rest. That is the whole customization story; there is no configuration file and no build step.

css
/* tier 1 — primitives. Not public API. */
--navx-color-gray-950: #0b0d0e;

/* tier 2 — semantic. A role, not a value. */
--navx-surface: var(--navx-color-gray-0);
--navx-text:    var(--navx-color-gray-900);

/* tier 3 — component. What the navbar reads. */
--navx-link-color: var(--navx-text);
--navx-nav-block-size: 4rem;

Make it yours

Three lines of CSS is a rebrand. No preprocessor, no theme object, no rebuild — these are custom properties, so they cascade, they respond to media queries, and you can change them at runtime.

css
/* Scope to the nav, or to :root for the whole page. */
.navx {
  --navx-accent: #0b5fa5;
  --navx-nav-block-size: 4.5rem;
  --navx-link-color-hover: var(--navx-accent);
}

/* They are real custom properties, so this works too. */
@media (prefers-color-scheme: dark) {
  .navx { --navx-surface: #0b0d0e; }
}
